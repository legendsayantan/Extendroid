== Abstract

This case study breaks down the internal architecture of Extendroid. It details how the system chains its rootless privilege, a custom IPC bridge, context forgery, undocumented API reflection, and raw telemetry interception to deceive the Android System Server.

By spoofing hardware states and execution lifecycles, Extendroid allows standard Android applications to execute headlessly and render remotely, unconstrained by conventional display or power limits.

== The Architectural Challenge: Android's Hostile Sandbox

Android is fundamentally designed to couple application lifecycles to physical hardware states, managed by services like `ActivityManager` and `PowerManager`.

If the physical screen is off, rendering is halted. If an app is not in the foreground, it is aggressively targeted by memory and power restrictions. To achieve remote execution while the host device is locked, the system must actively manipulate the framework's understanding of the device state.

== Step 1: The Privilege Vector (Escaping the Sandbox)

A standard Android application lacks the authorization to interact with restricted system managers.

**The Solution:** Extendroid relies on Shizuku for rootless privilege escalation. Shizuku allows the app to route API calls through a background process with ADB shell privileges (UID 2000). By binding a custom `RootService` to the Shizuku host, Extendroid inherits the authority to invoke hidden APIs.

_We now have the necessary privileges, but how does the sandboxed application communicate with this privileged service?_

== Step 2: The IPC Bridge (`IRootService.aidl`)

With the `RootService` running in a separate, privileged process, a robust communication channel is needed.

**The Solution:** Extendroid uses AIDL (Android Interface Definition Language) to define a formal IPC contract. The `IRootService.aidl` file defines all privileged operations. The Android build tools generate a thread-safe `Stub` and `Proxy` class, creating a secure command bus between the app's UI and the `RootService`.

_With a communication bridge in place, we can now create an isolated environment to run apps without disrupting the host device's physical screen._

== Step 3: Sub-Surface Execution (Creating the Environment)

Running apps off-screen requires decoupling the execution environment from the physical display. The public `MediaProjection` API is unsuitable due to its conspicuous "Screen Recording" indicator and a one-session limit.

**The Solution:** Extendroid forces the `DisplayManager` to create a display by spoofing the request's origin.
1.  **Identity Manipulation:** The system calls `clearCallingIdentity()`, ensuring the request runs under the privileged `RootService` context.
2.  **Context Forgery (`FakeContext`):** Using reflection, the `DisplayManager` is instantiated with a forged `Context`, severing the new display's ties to the host application's lifecycle.
3.  **Flag Fallback Matrix:** To bypass OEM restrictions, the system brute-forces a prioritized array of bitwise display flags, combining public and undocumented flags until the OS accepts the payload.
4.  **Android 14+ Compatibility:** To handle newer Android versions that restrict internal API access, the system uses a custom `ClassLoader` pointed at `/system/framework/services.jar`. This allows it to load the `com.android.server.display.DisplayControl` class directly, ensuring forward compatibility.

_This successfully spawns a hidden, untracked virtual display. But we still have another problem to solve: Android's power management forces virtual displays into a suspended, non-rendering state when the primary physical display turns off._

== Step 4: Power Mode Controlling (Keeping the Environment Alive)

When the physical screen times out, Android suspends rendering on all displays, including virtual ones. To run headlessly, the rendering pipeline must remain active.

**The Solution:** Extendroid takes control of the *main* physical display's power state. It uses reflection to access hidden `IPowerManager` APIs and programmatically set the display's power mode to "off."

Because these hidden APIs have shifting signatures across OEM devices, this is achieved with a **Signature Fallback Matrix**. The code loops through an array of potential method signatures (e.g., `wakeUp(long, int, String)`, `wakeUp(long, boolean)`) and catches `NoSuchMethodException` until it finds and invokes the correct one for the specific device.

This preempts the standard lockscreen timeout, preventing the OS from entering a deep sleep state that would suspend the virtual environment.

_Our environment is now alive, hidden, and immune to Doze constraints. But how do we actually get an app to launch inside it instead of popping up on the user's physical screen?_

== Step 5: Remote App Launching (Populating the Environment)

A standard `Intent` would either launch an app on the default display or be blocked by background execution limits.

**The Solution:** Extendroid launches apps directly into the headless virtual display using a custom `ActivityOptions` bundle.
*   The bundle is built via reflection, specifically setting the `launchDisplayId` to the virtual display's ID.
*   The launch is executed by invoking `startActivityAsUser` directly on the `IActivityManager` binder interface.
*   Before invocation, the `callingPackage` is spoofed as `com.android.shell`, granting the request elevated privileges and bypassing system permission checks.

_The app is now running and rendering invisibly. But a headless app is useless without a way to view and control it remotely. We need to connect the user._

== Step 6: Video Pipelining (Local Popups & Remote Streams)

The output buffer of the app running on the virtual display must be routed to a destination for viewing.

**The Solution:** Extendroid dynamically pipes hardware frames to their destination.
*   **Local Popups:** A `TextureView`'s `SurfaceTexture` is wrapped in a native `Surface` and passed to the `VirtualDisplay`. `SurfaceFlinger` then composites the headless app's frames directly onto the `TextureView` in real-time.
*   **Remote Streaming:** A custom WebRTC `VideoCapturer` provides an EGL-backed `Surface` to the `VirtualDisplay`. As `SurfaceFlinger` renders frames, they are intercepted at the GPU level, converted into WebRTC `VideoFrame` objects, and pushed down the video sink pipeline.

_Now that we have successfully piped the video output to our destinations, we encounter another fundamental limitation: Android applications are inherently designed for fixed mobile screens. What happens when the user resizes their remote browser window or drags a local popup?_

== Step 7: Dynamic Resizability & Scalability (Native DPI Interpolation)

Simply stretching a video stream results in a blurry, distorted UI. To achieve true desktop-like windowing, the app's layout must be natively recalculated.

**The Solution:** When a resize event occurs, the new dimensions are pushed to the host device. Extendroid invokes `VirtualDisplay.resize(width, height, dpi)` on the active headless display. This API call triggers an internal configuration change, forcing `WindowManager` to perform a new layout pass, reflow text, and adjust DPI as if the physical hardware had changed.

_With the environment fully scalable and the video piped securely, we need to handle the network signaling required to connect a remote user._

== Step 8: Distributed Edge Signaling (Connecting the User)

A persistent WebSocket for signaling would drain the host's battery.

**The Solution:** Extendroid uses a serverless signaling architecture with on-demand wakeups.
*   **Serverless Signaling:** A Cloudflare Worker manages session states (SDP/ICE candidates) using Durable Objects, avoiding the need for a dedicated signaling server.
*   **FCM Wakeups:** To initiate a connection from a cold start, the worker sends WebRTC payloads via FCM data messages. This bypasses battery restrictions and allows the host to wake up and connect.
*   To overcome FCM's 4KB payload limit, the worker first checks the payload size. If it's too large, it stores the data in a Durable Object and sends a simple `{ fetchsdp: true }` flag, prompting the host to retrieve the full payload via a secure HTTPS callback.

_We can now see the remote app and its state on our web client. However, we still have two final problems to solve: we cannot interact with it yet, and if the host device is locked, we are stuck looking at the Keyguard._

== Step 9: Synthetic Event Replay & Keyguard Evasion (Controlling the Environment)

Android strictly prohibits background services from injecting touch events and defends the Keyguard from programmatic bypasses.

**The Solution:** Extendroid uses raw telemetry interception and simulated user interaction.
*   **Input Translation:** The React client intercepts DOM events, translates them into Android `MotionEvent` commands, and sends them over a WebRTC data channel. The host then parses these commands and injects them into the `InputService`.
*   To solve UI glitches on mobile browsers known as "ghost clicks," the React client's touch listeners are registered with `{ passive: false }`, allowing it to call `e.preventDefault()` and swallow the unwanted events.
*   **Remote Unlock:** To bypass the lock screen, the system simulates a full user interaction sequence:
    1.  *Wake Device:* It invokes a robust `wakeUp` method that uses a fallback chain (hidden APIs, PowerManager, WakeLocks, shell commands) to ensure the device wakes up across different OEM hardware.
    2.  *Capture Gesture:* During a one-time training phase, `DevInputReader.kt` reads the raw binary event stream from `/dev/input/event*` to create a pristine model of the unlock gesture.
    3.  *Scale Coordinates:* Before replay, it calculates a scaling factor by parsing the output of `getevent -p` and `wm size` to map the raw input coordinates to the physical screen resolution.
    4.  *Replay Gesture:* The system replays the gesture. To prevent timestamps from becoming stale after a reboot, they are stored as deltas from the start of the gesture and recalculated against the current `SystemClock.uptimeMillis()` during replay.
    5.  *Sleep Device:* Once unlocked, a similarly robust `goToSleep` method is called to turn the physical screen off, saving battery.

This cycle allows Extendroid to programmatically bypass the Keyguard by mimicking a real user, without touching restricted Keyguard APIs.

== Conclusion

Extendroid is an exercise in architectural circumvention and distributed system design. By treating the Android Framework not as a strict set of rules, but as a state machine vulnerable to spoofed telemetry and context forgery, it successfully abstracts the localized mobile OS into a decoupled, distributed compute node. Paired with a serverless edge signaling broker and a zero-latency WebRTC client, it achieves sovereign remote application execution without compromising host constraints.
